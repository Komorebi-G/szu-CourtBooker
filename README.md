# 深大场馆预约 · SZU Court Booker

一个在本机运行的深圳大学体育场馆预约工具。登录后选择运动、日期和时段，确认后开始预约；未放号时等待 12:30，已放号时立即尝试。场地暂时无空位时继续查询；学校拒绝、账号异常或时段过期时停止相关尝试并显示原因。

提供 **Windows 桌面单文件版**和 **Android 前台版**，共用预约规则。桌面源码也支持 Linux。项目与学校无隶属关系，不保证抢到场地，不自动付款或退订。

[下载发行版](https://github.com/Komorebi-G/szu-CourtBooker/releases) · [桌面文档](desktop/README.md) · [Android 文档](mobile/README.md) · [问题反馈](https://github.com/Komorebi-G/szu-CourtBooker/issues)

## 先选适合你的版本

| | Windows 桌面版 | Android 版 |

| 运行依赖 | 不用安装 Node.js / npm | 不需要电脑或服务器 |
| 登录 | 浏览器登录或导入 Cookie / JSON | App 内学校登录或导入 Cookie / JSON |
| 多用户 | 支持，预约绑定账号 | 支持，预约绑定账号 |
| 到点执行 | 点击开始预约，自动判断等待或立即尝试 | 点击开始预约，自动判断等待或立即尝试 |
| 运行条件 | 助手程序保持运行，电脑醒着且联网 | 执行时保持亮屏，切后台即中断 |
| 中断处理 | 不自动补跑，保留结果，核对后手动重新启动 | 重开不自动执行，保留结果供核对 |

**当前版本 1.5.8，预发布测试版。** Windows EXE 未做代码签名；Android APK 使用开发签名。Android 学校登录、验证码和设备生命周期尚待真机验收。不要把编译成功理解为所有机型都已经测试通过。iOS 暂不支持。

## 下载与开始使用

本地构建输出在 `dist/SZU-CourtBooker.exe` 和 `dist/SZU-CourtBooker-Android.apk`；发行附件统一放在 `dist/release/`，以其中的 `release.json` 版本和 SHA256 为准。重新构建两端后运行 `npm run release:prepare` 同步发行目录；脚本会拒绝混用旧版本。运行中的旧 EXE 不会因重新打包而更新，需停止执行、退出旧程序后再打开新版。

### Windows

1. 在 [Releases](https://github.com/Komorebi-G/szu-CourtBooker/releases) 下载 `SZU-CourtBooker-Windows-x64.exe`。无需下载 GitHub 自动生成的源码压缩包。
2. 把 EXE 放在固定位置，双击启动。启动提示出现后，管理网页会自动打开；程序不会弹黑色终端。
3. 在「账号管理」登录或导入账号；新建预约，选择运动、日期、时段和场地；普通预约无需调整目标和参数。
4. 点击「下一步」核对安排，再点击「开始预约」，重新验证登录后等待放号或立即尝试。未来开放日只保存设置，开放当天再手动开始。
5. 本次执行期间保持助手程序运行、电脑醒着且联网。关闭网页标签不会停止已启动的本次执行；退出助手会停止全部执行并保存在途结果。

停止请用「停止本次执行」；关闭助手可点击网页右上角「···」菜单内的「退出应用」，或右键 Windows 右下角托盘图标选择「退出并停止执行」。关闭网页标签后，重新双击 EXE 可打开管理页面。新版不注册系统定时、不自动补跑。首次打开时停用当前数据目录的旧定时项，保留方案和结果；清理失败会在页面提示。更新前先停止旧版本正在运行的执行，旧进程不会自动升级；其他副本或数据目录的旧任务需分别停止。

### Android

1. 下载 `SZU-CourtBooker-Android-debug.apk` 并安装。已有同签名版本可覆盖安装；不要先卸载，否则本地数据会被清除。
2. 在首页点击「登录学校账号」完成学校认证；识别 Cookie 并核对身份后保存。已有用户用「重新登录」更新，也可导入/导出完整登录 JSON。
3. 首次登录成功后直接选择运动、日期和一至两个时段；时段和场地自动加载，默认不限场地。点击「下一步」核对安排，再点击「开始预约」。放号前自动等到当天 12:30，已放号时立即尝试，未来开放日只保存。多账号、备注、目标与重试参数在可选设置中，批量预约从「查找与批量预约」主动进入。
4. 等待与执行期间保持 App 在前台，不锁屏、不切换 App。离开前台后会停止后续请求，返回不会自动续跑。
5. 在「记录」查看成功时段和订单，再到学校系统付款。普通失败在原任务「重新预约」，部分成功「继续预约」，开始前自动跳过学校已有时段；结果未知的请求先在记录中刷新或到学校确认。

登录网页若不能正常打开，可先从桌面版导出登录 JSON 再导入手机。使用不同签名构建的 APK 可能无法覆盖安装，卸载前先导出需要保留的信息。

## 日常使用更方便

- 首页以方案列表为主，仅在需登录、执行中或有待处理结果时显示状态提示；待确认订单优先显示，即使使用日期已过去。
- 搜索与筛选收在「查找预约」，手机的批量选择需要主动进入；桌面还支持按账号筛选。已过期且无未知结果的预约保留在「全部」。
- 卡片「更多」里的「换日期再约」打开新的编辑器，保留时段、场地顺序、账号与重试设置。过去日期默认改为明天，仍在可选范围内的未来日期保留；请确认新日期。旧执行身份与相邻场地锚点清除，进入确认页不会下单。
- 表单以运动、日期、时段和场地为主，默认自动判断单段或两段目标；账号选择仅在有多个账号时显示，其他参数放在可选设置中。未来放号日的方案可保存，当天才能启动。
- 完成预约后优先查看结果与学校付款入口。Android 普通失败和部分成功可在原任务重新或继续预约；桌面保留只读核对后另存剩余方案的入口。修改后的方案不会把旧结果显示成当前预约。
- Android 已成功部分时段后手动停止，可继续原预约；只读配置检查失败不会冒充预约失败。手机保存期间防止重复提交，写入失败时保留原方案、账号和结果，并保留表单供重试。

## 预约规则

- 日期可选今天到未来第七天。一个任务可含多个候选时段，不是按星期循环执行。
- 固定放号时间为预约日期前一天北京时间 **12:30**。仅在放号当天手动启动倒计时；已放号可立即捡漏。保存方案本身不下单。
- 按点击顺序尝试场地，数字表示优先级。「优先同一场地」优先于场地顺序：例如顺序 A→B→C，前段约到 C，后段先尝试 C，失败再尝试 A→B；后段先成功后，补抢相邻前段也按此规则。未开启时各时段按原顺序尝试；不连续的时段不继承同场偏好，不会为换场退订。排球默认开启，羽毛球默认关闭。两端均可选择优先场地失败后继续尝试其余场地，默认只尝试已选场地。
- 预约目标可选「任选一段」「连续两段」「任意两段」。未设置目标的旧方案沿用「任意两段」。连续目标按当前仍可执行的候选与剩余名额判断组合，过期或冲突的邻段不能使孤立候选变成可行组合；第一段成功后仅补相邻时段，仍可能只成功一段，已约场地保留。
- 开始提交前只读核对学校订单。同一学校账号、同一项目、同一天，学校确认仍有效的预约与本批次新成功合计 **两个时段**后按工具现有上限停止提交（尚未核实为学校统一限额）。并发任务共享核对和计数；不同用户、项目和日期独立计数。已有的相同时段预约会复用，避免重复下单；场地不符合本方案选择或时段重叠时显示冲突。每个新批次重新核对，不直接把本地历史记录计入名额；学校查询失败或记录无法识别时停止该账号、项目、日期的尝试。
- 场地列表合并已开放参考日期的全部时段，并保留此前读到的目录，满员或暂不可用的条目仍可作为候选；它不代表目标日期和时段一定有空位。持续捡漏按目标日期逐时段查询，只向学校标记可预约的场地提交；满员响应后重新查询，不会拿后段目录当作前段空位。前段无空位、暂未开放或目录短暂网络故障时继续后段，在执行窗口内重试前段；单个场地未开放时继续尝试其他候选场地。已开始的候选时段会跳过。结果会区分全部成功、部分成功、名额上限跳过、时段过期、未约到和执行错误。
- 若学校返回账号异常或明确但无法识别的业务拒绝，执行会显示原始原因，同一学校账号的其他方案也停止提交；预约请求已发出却没有明确结果时，记录为待核对，先到学校“我的预约”核实。
- 中断后不自动恢复，历史成功和结果未知的请求会保留。Android 重新开始原任务时自动查询学校订单并排除已约时段；仅未知请求需在记录中刷新或人工确认。桌面可只读核对后另存剩余方案。未知或不完整记录不能当作没有订单。学校已有预约及最终限制以学校接口为准。
- 新建任务默认 **0.1 秒**提交起始间隔；前单响应和保存已经耗过该间隔时，后单尽快衔接，查询不会重新计时。持续捡漏按设定间隔查询空位，不另加固定数秒等待。学校明确提示频率限制时，同账号查询与提交共用退避；首次等待 1 秒、再次等待 2 秒，仍连续被拒绝则结束此账号本轮自动预约，避免持续刷单。这是客户端重试预算，不是学校公布的风控阈值；学校的更长 Retry-After 优先。查询成功不会清除连续提交拒绝。同一学校账号跨时段、方案、项目和日期均串行提交，前单完整响应并保存后才发后单，无双提交开关；不同账号独立。已有任务保留原间隔。长时间执行每 30 秒重新核验登录与订单，更新外部新增或取消的占用；本批次已确认成功不会因学校列表短暂延迟而丢失。
- 倒计时在放号前 15 秒核验登录与订单、预读候选目录并提前保存首单意图，匹配的两段意图分别保留，到点可复用。两端只选一个固定场地且不允许其他场地时，可利用匹配的本机场地结构省去到点查询；仅限放号后前 2 秒内各候选的首次提交，失败或窗口结束后重新查询。持续捡漏始终查询实时空位。空目录在放号后查询。临近放号用少量整秒边界样本更新时钟偏差并记录估计误差，不能保证毫秒级精度。一个账号的未知响应停止该账号，不拖住其他账号；本地存储失败停止整个批次。
- 不自动付款、不自动退订，不绕过学校身份认证、名额或时间限制。

桌面编辑方案后，旧日期和旧选择的执行结果保留在日志中；新方案显示未启动。配置检查不会遮住真实预约结果。页面断线时显示最后同步时间，倒计时继续作本地估算并自动重连；验证启动期间点击返回或关闭确认会取消这次启动。场地顺序可直接上移 / 下移，目录可就地刷新；提供可选的重试参数。完成结果附学校核对 / 付款入口，桌面可开启结果通知。

**登录不是永久有效的。** 保存的 Cookie 和过去的验证成功都不能保证放号时仍能使用。请临近放号时验证或重新登录；启动与倒计时结束后会联网检查，失效时停止。不要依赖隔夜保存的登录态无人值守预约。

本工具保存的是 `ehall.szu.edu.cn` 场馆预约请求使用的 Cookie，不保存校园网络接入凭据，也不把统一认证站点的 Cookie 写入账号文件。场馆页使用[统一身份认证](https://authserver.szu.edu.cn/authserver/login?service=https%3A%2F%2Fehall.szu.edu.cn%3A443%2Fnew%2F)；其“7 天免登录”不等于场馆 Cookie 保证有效 7 天。学校的只读响应会更新 `_WEU`，工具会保存更新。PC 端学校登录可选择浏览器；每种浏览器使用独立于日常窗口的助手配置，登录等待中可取消并重新选择。新增用户的浏览器登录先显示学校姓名和学号尾号，确认后才绑定；同一学校身份不能重复绑定成多个用户。已绑定账号的场馆会话失效时，助手会尝试用该浏览器仍有效的统一认证会话恢复同一账号的场馆登录。统一认证失效后仍需人工登录。Android 登录窗口会尝试沿用本 App 的学校会话，新增用户同样确认身份，换号时可手动清理。手机执行批次各账号独立预检，失效账号单独停止；不会弹出登录窗口干扰其他方案，请执行前验证 / 重新登录。

## 数据与隐私

账号、Cookie、任务和日志留在你的设备。Windows 单文件版存放于 `%LOCALAPPDATA%\SZUCourtBooker`；源码版使用本地 `config.yaml`、`.session.json`、`.data/`；Android 使用 App 私有目录。

导出的 Cookie / JSON 可以代表账号访问学校系统，请勿公开上传。仓库与发行包不含真实账号、Cookie、预约任务或订单。桌面管理服务没有远程认证，不要开放到公网；WSL 访问边界详见 [安全说明](SECURITY.md)。

项目规则依据已观察到的接口实现，学校接口可能变化。遇到提交超时等未知结果时，先核对学校订单，避免盲目重试。反馈问题时请脱敏，不要把登录 JSON 发到 Issue。

排查问题时，桌面在「日志 → 导出诊断记录」，手机在「记录 → 记录菜单 → 导出记录」取得诊断 JSON。记录包括执行时的参数、场地选择理由、每次尝试的编号/耗时/业务码、各时段最后结果、累计统计、构建标识和匿名账号分组，过滤登录凭据、学校账号标识及订单号字段。桌面每次执行另存最多 8 MiB 的追加日志，界面保留最近 500 条；手机保留最近 300 条。超出容量后仍保留原参数和全程统计，导出会注明缺失条数；成功和待核对预约另行保留。日志只是本地记录，导出不会自动上传。

## 源码运行

需要 Node.js 22 或更新版本。以下命令均从仓库根目录执行：

```sh
npm ci
npm run web -- --no-open
```

访问终端显示的本机地址，默认 `http://127.0.0.1:4173`。首次启动自动建立空白配置；不会生成预约任务。不依赖 Windows 任务计划或 Linux 用户定时器。

```sh
# 不访问学校的自动化测试
npm ci --prefix mobile
npm run check

# Android 界面构建
npm ci --prefix mobile
npm run build --prefix mobile

# Windows x64 单文件构建
npm run build:windows

# Android APK：另需 JDK 21 与 Android SDK 36
npm run apk --prefix mobile
```

Windows 打包需要与当前 Node 同版本的 Windows x64 `node.exe`；用 `SZU_WINDOWS_NODE` 指定路径。详见 [桌面文档](desktop/README.md)、[Android 文档](mobile/README.md) 与 [开发约定](CONTRIBUTING.md)。npm 只用于开发和构建，发行包的使用者不需要它。

## 仓库结构

```text
desktop/
  src/          桌面管理服务、账号文件、本次执行与旧任务清理
  web/          桌面管理界面
mobile/
  src/          手机界面、前台执行、学校登录状态保存
  android/      Android 原生工程与插件
  scripts/      手机构建脚本
shared/         两端共用的学校协议、预约规则与会话格式
src/            旧入口兼容层（旧定时入口只清理、不预约）
scripts/        桌面打包、登录和验收工具
test/           模拟数据自动化测试
docs/           发布流程与版本说明
```

本地的 `dist/`、`.build/`、`.data/`、`output/`、设计草稿和浏览器调试记录均不进入 Git。不复制两套预约核心，也不把桌面调度逻辑塞进手机版。
