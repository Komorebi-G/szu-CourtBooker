# 共用预约逻辑

桌面端和 Android 端共用此目录，禁止导入 Node 文件系统、桌面调度器或 Android 原生插件。

- `api.js`、`http-client-core.js`：学校协议与可注入传输层。
- `runner.js`、`planner.js`、`booking-quota.js`：放号等待、场地顺序、同场偏好及两时段上限。
- `session-format.js`：登录 JSON / Cookie / cURL 解析。
- `diagnostics.js`：诊断参数快照、累计统计、字段过滤和诊断导出。
- `projects.js`、`constants.js`、`utils.js`、`errors.js`：项目目录及公共工具。

桌面端注入 Node HTTP 和持久化，Android 注入原生 HTTP 和本地文件存储。规则测试位于根目录 `test/`。

## 组合规则与排查

正式执行的场地视图按日期、时段区分；界面和只读检查共用跨已开放日期、全部时段的参考目录，并合并历史结构缓存；不得在第一个有数据的日期提前返回，也不得虚构默认查询时段。参考读取先汇总各日期、显式配置和有效缓存时段，再逐日期补查整个并集；缓存只保留场地结构，执行不得借用其他日期或时段的场地视图。每个候选读取完就可以尝试，不必等后续候选目录。空目录、明确未开放及可识别的短暂网络故障不会终止其他候选；身份异常、畸形响应和未知业务拒绝仍显示原因并停止。

倒计时在放号前最后 15 秒复核身份与学校订单，在准备窗口内逐个预读候选时段；只读请求受短超时和准备截止时间约束，为最后 3 秒校时留出时间。通过 `onPreparedAttempt` 提前持久化首选预约意图，匹配的首单到点无需再等全量状态保存；候选改变时重新保存，未发出的准备项在结束时清除。已有目标视图到点直接尝试，后续已预读时段不用再排队查询；未开放或空目录到点重读。明确尚未放号时下一轮重试首选，单个场地未开放仍可继续其他场地。

`server-clock.js` 将秒级 HTTP Date 与请求起止时间转为偏差区间，多次取交集并报告区间宽度；临近放号利用新鲜估计在整秒边界再次取样，失效、缓存、冲突与超时明确回退，不能宣称毫秒级校准。最后一秒缩短等待步长，预约仍按估计的放号时间发送。传输调用日志不证明学校收件或受理时间。学校已返回明确业务结果后发生 Cookie 保存异常，保留该结果并停止相关作用域；成功不得降为未知，失败不得盲目重发。

开启同场偏好时，先参考已成功的相邻前段；没有成功前段则参考已成功的相邻后段。只从当前时段允许的场地候选中提升该场地，失败回到原用户顺序，再按开关决定是否补充其余场地；不会跨过不连续时段继承偏好，不会重发成功时段或自动退订。各并发方案仍受同账号/项目/日期两时段上限约束，成功可以分散到多个方案，各自如实显示部分成功。

`test/booking-combinations.test.js` 覆盖同场偏好、其余场地、并发度与前段空目录/未开放/503/无空位的组合，以及后段先成功再补前段、低优先场地继承、同场失败回退和逐时段及时提交。真实学校接口仍需现场验证。

诊断事件类型包括 `execution_plan`、`catalog_query`、`court_order`、`booking_request`、`booking_dispatch`、`booking_response`、`booking_error` 和 `execution_summary`。请求编号在同一次方案执行中关联准备、传输调用、响应或异常；手机批次额外包含 `planId`。`booking_dispatch` 表示交给传输层，不表示学校收到或预约成功。名额队列等待、传输前等待、完整尝试耗时和可取得的 HTTP 耗时分别记录。

两端均保留初始参数、按时段累计统计和独立结束统计；桌面额外追加 `events.ndjson`（每次执行最多 8 MiB），手机保留最近 300 条事件。导出格式是 `szu-court-diagnostics/v1`，包含事件序号及 `missingEvents`，容量截断须明确显示。日志快照合并至最多每 200ms 一次，提交前必须已有持久意图，已确认结果仍立即保存；桌面追加日志使用独立写队列，结束时完整等待，日志写入失败停止后续提交。不同学校账号独立提交，同账号串行至结果保存完成；未知响应只停止对应账号，存储故障停止整个批次。手机使用 `pendingRequests` 保存全部并行意图，并兼容旧 `inFlight`。不得把 Cookie、请求头、请求表单或完整原始响应加入日志。

预约目标由 `booking-goal.js` 校验和判断（one / consecutive / two），连续目标的邻段必须仍可执行且剩余名额足以补成一对，排队实际下单前再次判断。两端向 `runner.js` 注入只读学校订单查询；同账号、项目、日期通过 `booking-quota.js` 共享一次核对，学校有效预约与本批次新成功合计限制为两段。这是工具现有上限，尚不能当作已经核实的学校统一限额。同作用域的执行全部结束后，再次手动启动重新查询；其他作用域仍在等待也不能保留已结束作用域的旧占用或拒绝。不直接使用本地历史作为占用依据；查询失败或字段/状态未知时停止相关作用域。相同时段可复用，不符合场地选择或与已有时段重叠时显示冲突。账号异常、未知提交结果、未知业务拒绝或连续频率拒绝在名额队列释放前写入账号共享停止原因，同账号其他项目和日期也停止提交，其他账号独立。固定场地结构可供两端倒计时准备首次提交，但不作为持续捡漏的空位证据。

`booking-review.js` 保守解析学校订单、排除已约或重叠候选并计算当天占用。未知记录和未对应的本地成功/待确认记录，即使时段未选中或仅部分重叠也须人工核对，不将未知状态或失败查询当作空订单。剩余方案携带已核对的相邻场地标识；实际执行仍重新查询学校占用。

`experience.js` 共用两端的展示逻辑：上海日期与放号提示、方案筛选排序、复用字段清理、连续候选汇总和手机执行版本匹配。同时提供操作菜单的视口定位与收起行为，不取代学校核对、账号验证、名额与执行启动校验。桌面仅通过 `/experience.js` 提供该浏览器模块，手机将其打入本地资源。
